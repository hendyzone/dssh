# Team Service Protocol (`dssh-team.v1`)

Status: **draft for review** · Protocol version: `v1` · Schemas: [`docs/schemas/`](schemas/)

This document is the normative wire contract between the dssh team service and its
three kinds of clients: the dssh desktop app, the Lead tooling (skill client / CLI), and
the per-machine report agents. It replaces the earlier model in which every client read and
wrote a roster JSON file over SSH (`apps/desktop/src-tauri/src/team_members.py`).

The service implementation lives in a separate repository. This repository only carries the
contract and test doubles built against it. All hosts, projects, and addresses in this document
are placeholders (`team.example.invalid`, `example-project`, `host-a`).

Keywords **MUST**, **SHOULD**, **MAY** are used as in RFC 2119.

---

## 1. Overview

```
desktop ──REST (read/write)──┐
desktop ──WS  (push only)────┤
lead    ──REST (read/write)──┼──► team service ──► SQLite (roster, events, AI)
lead    ──WS  (optional)─────┤          ▲
agent   ──POST /agent/report─┘          └── AI summarizer (server side only)
```

- **Roster** (who is on a project, where their tmux session lives, notes) is durable state.
  Every committed change bumps a per-project sequence number `seq` and is recorded as an event
  that can be replayed over WebSocket.
- **Live state** (is the member's tmux session there, what is it doing) comes from report
  agents. It is volatile, never persisted, never replayed, and versioned by `lseq`.
- **AI summaries** are generated by the service only. Clients read them; any client write of an
  AI field is rejected.
- The WebSocket is **push-only**. All writes go through REST.

Base URL: `http://team.example.invalid:8093/api/v1`. The service is intended for private
networks only; it does not terminate TLS. A token is required on every endpoint except
`/health`, regardless of source address — a source-address allowlist is an extra filter, never
authentication (connections arriving through a tunnel or reverse proxy all look local).

Conventions:

- Bodies are UTF-8 JSON (`Content-Type: application/json`).
- Member and AI objects use `camelCase` (inherited from the legacy roster file); live, machine
  and agent objects use `snake_case`.
- Server-generated timestamps are RFC 3339 UTC strings (`2026-10-25T05:32:00.123Z`).
  tmux-originated times (`created`, `activity`) are integer Unix seconds, because they are part
  of a session's identity.
- A **session key** is `"<tmux session id>:<session created>"`, e.g. `"$3:1712345678"`.
- String lengths are counted in Unicode code points (Python `len`, Go `utf8.RuneCountInString`),
  never bytes. Byte limits are stated as bytes explicitly.
- Integers MUST be written as JSON integers. `1.0` or `1e3` are rejected even where JSON Schema
  would accept them (the legacy validator rejects them; JSON Schema `"type":"integer"` does not).

## 2. Authentication and roles

Every request except `GET /health` carries `Authorization: Bearer <token>`. Tokens are opaque;
the service stores only their SHA-256. Tokens are issued exclusively through the service's local
CLI on the service host. **There is no HTTP endpoint that creates, lists, or revokes tokens.**

| Role | Bound to | Allowed |
|---|---|---|
| `lead` | exactly one project | read roster/live/AI/machines of that project; write roster (`PUT`/`PATCH`/`DELETE`); import/export; request AI refresh; WS subscribe to that project |
| `desktop` | all projects (`"*"`) or an explicit project list | read; write roster (`PUT`/`PATCH`/`DELETE`); request AI refresh; WS subscribe |
| `agent` | exactly one machine name | `POST /agent/report` and `GET /me` only |
| worker | — | **no token is ever issued to worker agents** |

The machine an agent reports for is taken **from its token**, never from the request body.
(Two machines may share a hostname; the token is the identity.)

Authorization failures:

- missing/unknown/revoked token → `401 unauthorized`
- valid token, wrong role for the endpoint → `403 forbidden`
- project outside the token's scope → `403 project_forbidden`
- source address outside the allowlist → `403 source_forbidden`
- any client attempt to write an AI field → `403 ai_fields_forbidden` (§4.10)

**Auth-failure throttling:** a source address that produces more than 20 `401`/`403` responses
in a rolling minute receives `429 rate_limited` (with `Retry-After`) on further requests that
carry **no token or an invalid/revoked token** until the window clears. Requests with a valid
token are never throttled by this rule: several clients often share one source address (NAT,
tunnels, one host running both an agent and a desktop), and one misconfigured client must not
lock the others out. `403` for a valid token with the wrong role does not count as a failure.

## 3. Errors

Every non-2xx response with a body uses one shape ([`error.json`](schemas/error.json)):

<!-- schema: error.json -->
```json
{"error": {"code": "rev_mismatch", "message": "member was modified; re-read and retry", "field": "If-Match"}}
```

| Status | `code` values | Meaning |
|---|---|---|
| 400 | `bad_json` | body is not parseable UTF-8 JSON, or not the expected top-level type |
| 401 | `unauthorized` | missing, unknown, or revoked token |
| 403 | `forbidden`, `project_forbidden`, `source_forbidden`, `ai_fields_forbidden` | see §2 |
| 404 | `not_found`, `member_not_found` | unknown route; member key not in roster |
| 409 | `tmux_mismatch`, `no_live_session` | `DELETE` tmux identity does not match the stored member (§4.8); AI refresh with no exact live match (§4.11) |
| 412 | `if_match_required`, `rev_mismatch` | required precondition missing; precondition does not match current `rev` |
| 413 | `payload_too_large` | body exceeds the endpoint limit (§9) |
| 422 | `validation_failed`, `duplicate_member`, `roster_full`, `identity_immutable` | body fails §5 rules |
| 426 | `agent_outdated`, `upgrade_required` | agent below `min_agent` (§7.5); non-WebSocket request to the WS route |
| 429 | `rate_limited`, `budget_exhausted` | throttled; carries `Retry-After` (seconds) |
| 503 | `overloaded`, `ai_disabled` | connection cap reached; AI subsystem not enabled |

`message` is human-readable and MUST NOT be parsed. `field` names the offending field (dotted path,
e.g. `members.3.tmux.id`) when there is one. Clients MUST treat unknown codes by status class.

## 4. REST endpoints

All paths are relative to `/api/v1`. `{p}` is a project name (§5.1). `{key}` is a member key
(§5.2), percent-encoded (an email key contains `@`).

| Method | Path | Roles | Purpose |
|---|---|---|---|
| GET | `/health` | none | liveness |
| GET | `/me` | any | token identity |
| GET | `/projects` | lead, desktop | visible projects |
| GET | `/projects/{p}/team` | lead, desktop | full snapshot |
| GET | `/projects/{p}/team/members/{key}` | lead, desktop | one member |
| PUT | `/projects/{p}/team/members` | lead, desktop | batch upsert (1–100) |
| PATCH | `/projects/{p}/team/members/{key}` | lead, desktop | partial update |
| DELETE | `/projects/{p}/team/members/{key}?tmux=<session key>` | lead, desktop | remove |
| POST | `/projects/{p}/team/import[?replace=1]` | lead | import a legacy roster file |
| GET | `/projects/{p}/team/export` | lead | export as a legacy roster file |
| POST | `/projects/{p}/team/members/{key}/ai/refresh` | lead, desktop | request an AI re-summary |
| GET | `/machines` | lead, desktop | agent machines |
| POST | `/agent/report` | agent | live report (§7) |
| GET | `/team/ws` | lead, desktop | WebSocket, subprotocol `dssh-team.v1` (§6) |

A project that has never been written to but is within the token's scope returns an empty
roster with `seq: 0`; it is not a `404`.

### 4.1 `GET /health`

`200 {"ok": true, "version": "0.1.0"}`. No authentication, no other information.

### 4.2 `GET /me`

<!-- schema: none -->
```json
{"role": "desktop", "token_id": "tok_7f3a", "label": "desktop on host-a", "projects": "*", "machine": null}
```

`projects` is `"*"` or an array of project names; for an `agent` token it is `[]` and `machine`
is the bound machine name.

### 4.3 `GET /projects`

`200 {"projects": [{"project": "example-project", "seq": 42, "members": 3}]}` — every project
in scope that has at least one event, plus (for a `lead` token) its bound project.

### 4.4 `GET /projects/{p}/team`

`200` with a team snapshot ([`team-snapshot.json`](schemas/team-snapshot.json)) and
`ETag: "<seq>"`. `If-None-Match: "<seq>"` matching the current seq yields `304` with no body.

<!-- schema: team-snapshot.json -->
```json
{
  "project": "example-project",
  "seq": 42,
  "lseq": 1803,
  "members": [
    {
      "project": "example-project",
      "key": "worker-a@example.invalid",
      "email": "worker-a@example.invalid",
      "role": "implementation worker",
      "host": "host-a",
      "port": 22,
      "username": "dev",
      "workdir": "/srv/example-project",
      "tmux": {"id": "$3", "created": 1712345678, "name": "worker-example-project-host-a-codex"},
      "responsibilities": "backend API",
      "currentTask": "T7 storage layer",
      "updatedAt": "2026-10-25T05:32:00.123Z",
      "rev": 41
    }
  ],
  "ai": {
    "worker-a@example.invalid": {
      "status": "working",
      "summary": "running storage tests",
      "evidence": "ok  example/internal/store 0.41s",

      "source": {"machine": "host-a", "session": "$3:1712345678"},
      "model": "example-model",
      "updatedAt": "2026-10-25T05:30:10.000Z"
    }
  },
  "live": {
    "worker-a@example.invalid": {
      "key": "worker-a@example.invalid",
      "machine": "host-a",
```

`ai` and `live` are keyed by member key and contain entries only for current members.
`machines` lists every machine that holds an agent token.

### 4.5 Revisions and preconditions

- Every member carries `rev`: the project `seq` of the last write transaction that changed that
  member. It therefore only increases, and a member that is deleted and re-created never reuses
  an old `rev`. AI updates bump `seq` but do **not** change any member's `rev`.
- `GET …/members/{key}` and every write that returns a member set `ETag: "<rev>"`.
- **Position fields** are `host`, `port`, `username`, `workdir`, `tmux` (any sub-field).
  Changing any of them on an existing member requires a precondition:
  - `PATCH` / `DELETE`: header `If-Match: "<rev>"` (a bare integer is also accepted;
    `*` is treated as absent).
  - `PUT` batch: the item's `rev` field (a header cannot cover many members).
- Missing precondition where required → `412 if_match_required`. Precondition present but not
  equal to the current `rev` → `412 rev_mismatch`. A precondition supplied where it is not
  required is still checked.
- Creating a new member needs no precondition. A `rev` on an item whose key does not exist →
  `412 rev_mismatch` (the client believed it existed).
- Non-position changes (role, notes) without a precondition are last-writer-wins per field,
  the same as the legacy `memberNotes` operation.
- A write that changes nothing (stored member already identical) is a no-op: no `rev` bump, no
  event. If every item in a request is a no-op, `seq` is unchanged.

On `412`, clients SHOULD re-read the member (or snapshot), re-apply their intent, and retry once.

### 4.6 `PUT /projects/{p}/team/members` — batch upsert

Equivalent of legacy `memberBatch` / `memberSave`. Body: a JSON array of 1–100 member inputs
([`member.json#/$defs/memberInput`](schemas/member.json)). **All or nothing**: if any item fails
any rule, nothing is written.

- Items are identified by key (`email` if non-empty, else `id`). Two items with the same key →
  `422 duplicate_member`.
- Note fields (`responsibilities`, `quota`, `currentTask`, `notes`) **omitted** keep the stored
  value; an **empty string** clears it.
- Unknown fields are ignored (legacy behaviour), except AI fields (§4.10) → `403`.
- `key`, `updatedAt` in the input are ignored; the server sets `updatedAt`.
- The resulting roster must stay ≤ 100 members and ≤ 256 KiB (§5.4) → else `422 roster_full`.

<!-- schema: member.json#/$defs/memberInput[] -->
```json
[
  {
    "project": "example-project",
    "email": "worker-a@example.invalid",
    "role": "implementation worker",
    "host": "host-a",
    "port": 22,
    "username": "dev",
    "workdir": "/srv/example-project",
    "tmux": {"id": "$4", "created": 1712400000, "name": "worker-example-project-host-a-codex"},
    "rev": 41
  },
  {
    "project": "example-project",
    "email": "",
    "id": "member-reviewer-1",
    "role": "reviewer",
    "host": "host-b",
    "port": 2222,
    "username": "dev",
    "workdir": "/srv/example-project",
    "tmux": {"id": "$0", "created": 1712400100, "name": "worker-example-project-host-b-pi"},
    "notes": "reviews storage changes"
  }
]
```

Response `200 {"project": "example-project", "seq": 43, "members": [<stored member>, …], "ignored_fields": []}`
with members in request order. `ignored_fields` lists unknown top-level names seen in the batch (empty when none).

### 4.7 `PATCH /projects/{p}/team/members/{key}`

Equivalent of legacy `memberNotes` (plus position edits). Body: a member patch
([`member.json#/$defs/memberPatch`](schemas/member.json)), at least one property.

- Allowed: `role`, the position fields, the note fields. Same rules as §5.
- `project`, `email`, `id` MAY be present but MUST equal the stored values →
  else `422 identity_immutable`. To change identity, delete and re-create.
- `tmux` is replaced as a whole object (all three sub-fields required).
- Note-field semantics as in §4.6.

<!-- schema: member.json#/$defs/memberPatch -->
```json
{"currentTask": "T8 replay buffer", "notes": ""}
```

Response `200 <stored member>` with `ETag`; when the patch contains unknown top-level fields the response also
carries `ignored_fields` (sorted string array, key only added when non-empty). Unknown key → `404 member_not_found`.

### 4.8 `DELETE /projects/{p}/team/members/{key}?tmux=<session key>`

Equivalent of legacy `memberRemove`, with two guards that the legacy operation lacked:

1. `tmux` query parameter: the session key `"<tmux.id>:<tmux.created>"` the client believes
   the member occupies, e.g. `?tmux=$3:1712345678` (`$` and `:` are legal in a query; the
   percent-encoded form `%243%3A1712345678` MUST also be accepted). Missing or malformed →
   `422 validation_failed`. Not equal to the stored member's tmux identity → `409 tmux_mismatch`.
2. `If-Match: "<rev>"` — required (§4.5).

The tmux check is evaluated before `If-Match`. Response `200 {"project": "example-project", "seq": 44}`.
Unknown key → `404 member_not_found`.

### 4.9 Import and export (lead only)

`POST /projects/{p}/team/import` — body is the **content of a legacy roster file**: a JSON
array of ≤ 100 members, ≤ 256 KiB. Each entry is validated with §5 rules; legacy AI fields
(`aiSummary`, `aiStatus`, `aiUpdatedAt`, `aiDigest`, `aiSource`, `aiEvidence`) are **dropped,
not rejected** — AI state is regenerated by the service. No preconditions apply.

- default: merge — each entry is upserted as in §4.6;
- `?replace=1`: the roster becomes exactly the file; members not in the file are removed.

All or nothing; one event (one `seq`) for the whole import. Re-importing the same file is a no-op. Unknown
top-level fields are ignored and reported in `ignored_fields` (same shape as §4.6).
Response:

<!-- schema: none -->
```json
{"project": "example-project", "seq": 45, "upserted": 3, "removed": 0, "unchanged": 0, "dropped_ai_fields": 7, "ignored_fields": []}
```

`GET /projects/{p}/team/export` — `200`, a JSON array in the legacy file shape (members without
`key`, `rev` and AI fields), `Content-Disposition: attachment`. Intended for emergencies and
round-trip testing: `import?replace=1` of an export is a no-op.

### 4.10 AI fields are read-only

Clients never write AI data. A `PUT`/`PATCH` body (or any batch item) containing a top-level key
`ai` or any key matching `^ai[A-Z_]` → `403 ai_fields_forbidden`, checked before validation.
Import is the only exception (§4.9: dropped).

### 4.11 `POST /projects/{p}/team/members/{key}/ai/refresh`

Asks the service to re-summarize one member now (bypassing the digest/interval triggers of §8.1,
but not the budget). No body.

- `202 {"queued": true}`.
- `404 member_not_found`; `409 no_live_session` if the member has no `exact` live match (there
  is nothing to summarize).
- `429 rate_limited`: at most once per member per 30 s and 20 per token per hour.
- `429 budget_exhausted`: daily budget reached; `Retry-After` points at the budget reset.
- `503 ai_disabled`: AI subsystem not enabled on this deployment.

The result arrives as a `delta` with an `ai` op (§6.5).

### 4.12 `GET /machines`

`200 {"machines": [{"name": "host-a", "online": true, "seen": "2026-10-25T05:32:01.250Z", "version": "0.1.0"}]}`.
A machine is listed once an agent token exists for it; `seen`/`version` are `null` until its
first report.

## 5. Member object and validation rules

These rules are a port of `apps/desktop/src-tauri/src/team_members.py` and MUST behave the
same. The shared judgement fixtures (`roster_cases.json`, generated by running that Python
code) are the tie-breaker; where this text and the fixtures disagree, the fixtures win and this
text is a bug.

### 5.1 Project name

`^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$` (1–64 characters). Applies to `{p}` in paths and to every
`project` field. Every member's `project` MUST equal `{p}` → else `422`.

### 5.2 Fields

Definitions used below:

- **line text(N)**: a string that is not blank after trimming whitespace, at most N code points,
  and contains no control character U+0000–U+001F or U+007F.
- **note text**: a string of at most 2000 code points containing no U+0000–U+0008,
  U+000B–U+001F or U+007F. Tab (U+0009) and line feed (U+000A) are allowed; carriage return is not.
  Empty is allowed.

| Field | Rule | Stored member |
|---|---|---|
| `project` | §5.1, equals `{p}` | required |
| `email` | **required string**. Either `""`, or line text(254) that fully matches `^[^\s@]+@[^\s@]+$` (exactly one `@`, no whitespace) | required |
| `id` | `^member-[a-zA-Z0-9-]{1,80}$`. If `email` is non-empty, an invalid `id` is **silently dropped**; if `email` is empty, a valid `id` is required | optional |
| identity | `email` non-empty, or a valid `id` → else `422` | — |
| `role` | line text(80) | required |
| `host` | line text(255), and contains no whitespace and no `/` | required |
| `port` | integer 1–65535 (booleans and non-integers rejected) | required |
| `username` | line text(80) | required |
| `workdir` | line text(1024), starts with `/` | required |
| `tmux` | object, required | required |
| `tmux.id` | `^\$[0-9]+$` | required |
| `tmux.created` | integer, 1 ≤ n ≤ 9007199254740991 (2^53 − 1) | required |
| `tmux.name` | line text(255) | required |
| `responsibilities`, `quota`, `currentTask`, `notes` | note text | optional |
| `tenure` | `"resident"` or `"temporary"` (other values → `422`); omitted = legacy member, displayed as resident | optional |
| `for_task` | `<project>/<code>`: both segments match the project/code character sets, whole string ≤ 64 bytes (snake_case name inherited from dteam) | optional |
| `key` | server-derived: `email` if non-empty, else `id` | response only |
| `rev` | integer ≥ 1 (§4.5); in input, an expected-rev precondition | response; optional in input |
| `updatedAt` | RFC 3339, server-set on every change | response only (ignored in input) |

Unknown fields in input are ignored and never stored; unknown keys inside `tmux` are ignored. Write endpoints
do not silently drop them: `PUT` batch, `PATCH` and `import` responses carry `ignored_fields` (sorted string
array of the unknown top-level names) so callers can notice typos without being rejected.

Regex notes for implementers:

- `\s` means Unicode whitespace in both Python 3 `re` (str patterns) and ECMAScript `u` mode; the
  JSON Schemas use the same patterns.
- `tmux.id` digits are **ASCII only** in this protocol. (Python's `\d` would also accept other
  Unicode decimal digits; tmux never produces them, and the service rejects them.)
- The JSON Schemas cannot express "not blank after trim" exactly; they approximate it with "contains
  a non-whitespace character". The server rule above is normative.

### 5.3 Batch rules

- A `PUT` body has 1–100 items.
- Keys within one batch are unique → else `422 duplicate_member`.
- Validation is all-or-nothing.

### 5.4 Roster limits

After any write, the project roster MUST have ≤ 100 members and its export serialization
(§4.9, compact JSON, UTF-8, non-ASCII unescaped) MUST be ≤ 256 KiB (262144 bytes) →
else `422 roster_full` and nothing is written. Request bodies for `PUT` and import are capped at
256 KiB → `413 payload_too_large`.

## 6. WebSocket push channel

`GET /api/v1/team/ws` with `Authorization: Bearer <token>` and
`Sec-WebSocket-Protocol: dssh-team.v1`. A client that does not offer the subprotocol is refused
(`400`); a plain HTTP request gets `426 upgrade_required`. Authentication happens at the upgrade
(`401`/`403` as HTTP responses). When the global connection cap is reached the upgrade gets
`503 overloaded` with `Retry-After`.

Every frame is a text frame holding one JSON object with a `type` field
([`ws-client-message.json`](schemas/ws-client-message.json),
[`ws-server-message.json`](schemas/ws-server-message.json)). Clients MUST ignore unknown
server message types and unknown fields.

### 6.1 Client messages

<!-- schema: ws-client-message.json -->
```json
{"type": "sub", "projects": {"example-project": 42, "other-project": null}}
```

<!-- schema: ws-client-message.json -->
```json
{"type": "unsub", "projects": ["other-project"]}
```

<!-- schema: ws-client-message.json -->
```json
{"type": "ping", "id": "p-17"}
```

- `sub`: map of project → last applied `seq`, or `null` for "send me a snapshot". Repeating
  `sub` for an already subscribed project is allowed and re-runs §6.3 for it (this is how a
  client recovers from a gap).
- `unsub`: stop pushing those projects.
- `ping`: server answers `pong` with the same `id`.
- The client never writes roster data over WS. A malformed message gets
  `error{code:"bad_request"}`; the connection stays open.

### 6.2 Server messages

| `type` | Fields | Notes |
|---|---|---|
| `snapshot` | `project, seq, lseq, members, ai, live, machines` | same body as §4.4 plus `type` |
| `delta` | `project, seq, ops[]` | one committed write transaction; durable, replayable |
| `live` | `project, lseq, full, items[]` | live-state changes; volatile |
| `machine` | `name, online, seen, version` | agent machine came online / went stale / changed version |
| `pong` | `id?, time` | answer to `ping`, or heartbeat (no `id`) |
| `error` | `code, project?, message?` | `unauthorized`, `forbidden`, `resync`, `bad_request`, `overloaded` |

<!-- schema: ws-server-message.json -->
```json
{"type": "delta", "project": "example-project", "seq": 43, "ops": [
  {"op": "upsert", "member": {"project": "example-project", "key": "worker-a@example.invalid", "email": "worker-a@example.invalid", "role": "implementation worker", "host": "host-a", "port": 22, "username": "dev", "workdir": "/srv/example-project", "tmux": {"id": "$4", "created": 1712400000, "name": "worker-example-project-host-a-codex"}, "updatedAt": "2026-10-25T05:40:00.000Z", "rev": 43}},
  {"op": "remove", "key": "member-reviewer-1"}
]}
```

<!-- schema: ws-server-message.json -->
```json
{"type": "live", "project": "example-project", "lseq": 1804, "full": false, "items": [
  {"key": "worker-a@example.invalid", "machine": "host-a", "session": "$4:1712400000", "match": "exact", "state": "waiting_input", "detail": "", "since": "2026-10-25T05:41:02.000Z", "ctx_pct": 44, "model": "example-model", "last_line": "Do you want to proceed? (y/n)", "at": "2026-10-25T05:41:03.000Z", "stale": false}
]}
```

<!-- schema: ws-server-message.json -->
```json
{"type": "machine", "name": "host-b", "online": false, "seen": "2026-10-25T05:40:31.000Z", "version": "0.1.0"}
```

<!-- schema: ws-server-message.json -->
```json
{"type": "error", "code": "resync", "project": "example-project", "message": "seq 12 is older than the replay window"}
```

`forbidden` is sent for a `sub` naming a project outside the token's scope; other projects in the
same `sub` proceed normally. `unauthorized` is sent when the token is revoked during the
connection, followed by close code `4401`.

### 6.3 `seq`: roster and AI events, replay, resync

- `seq` is per project, starts at 0, and increases by exactly 1 per committed write transaction
  (a batch, a patch, a delete, an import, one AI update). Each transaction is one `delta`.
- The server retains the last 500 events or 24 hours of events per project, whichever is smaller.
- On `sub` with `lastSeq`:
  - `null` → `snapshot`.
  - equal to current `seq` → nothing for roster/AI (already up to date).
  - inside the retained window → every `delta` with `seq` in `(lastSeq, current]`, in order.
  - older than the window, or **greater** than current `seq` (e.g. the server was restored from a
    backup) → `error{code:"resync", project}` immediately followed by `snapshot`.
- After the roster part, the server always sends one `live` with `full: true` for that project.
  This doubles as the subscription acknowledgement.
- Client rule: apply a `delta` only if `seq == local + 1`; ignore `seq <= local`; on
  `seq > local + 1` re-send `sub` with the local value. A `snapshot` replaces all local state for
  the project (members, ai, live, machines).
- Delta ops: `upsert{member}` (full stored member), `remove{key}` (also discards that member's
  `ai` and `live` entries), `ai{key, ai}` (`ai: null` clears).

### 6.4 `lseq`: live state

- Live state is never written to the event table and never replayed.
- `lseq` is per project, increases with every `live` message, and resets when the service
  restarts. It is only meaningful within one connection.
- Changes are coalesced per project over 250 ms; `full: false` items replace the client's entry
  for that key. `full: true` replaces the whole live map for the project.
- On every (re)subscription the client gets a fresh `full: true` message; there is no live replay.
- Client rule: drop a `live` message whose `lseq` is not greater than the last applied one on this
  connection.

Live item fields ([`team-snapshot.json#/$defs/liveItem`](schemas/team-snapshot.json)):

| Field | Meaning |
|---|---|
| `key` | member key |
| `machine` | machine the member's `host` maps to (server-side address table), or `null` if unmapped |
| `session` | session key currently matched, or `null` |
| `match` | `exact`: a session with the member's `(tmux.id, tmux.created)` exists on that machine. `replaced`: no exact match, but a session with the same `tmux.name` and a different identity exists (`session` is that one). `gone`: neither. `no_agent`: the machine is unmapped or has no agent token — desktop falls back to its own data source |
| `state` | `running`, `waiting_input`, `input_pending`, `stuck`, `idle` (from the agent's classifier), or `unknown` (no classification yet, or `match` is `gone`/`no_agent`) |
| `detail` | classifier detail, e.g. a stuck category; may be empty |
| `since` | when `state` last changed |
| `ctx_pct`, `model`, `last_line` | context usage 0–100, model name, last visible line (clipped by the agent) |
| `tool` | Optional agent-observed process tool: `claude`, `codex`, `pi`, `dsh`, `cursor`, or `agy`. Omitted when unknown; never inferred from member roles or mailbox names. |
| `at` | time of the agent observation this item reflects |
| `stale` | `true` when the machine's agent has not reported for 30 s; values are the last known ones |

### 6.5 AI push

AI records are part of the durable state: each update is a `delta` with one `ai` op and its own
`seq`, so they are replayed like roster changes.

<!-- schema: ws-server-message.json -->
```json
{"type": "delta", "project": "example-project", "seq": 46, "ops": [
  {"op": "ai", "key": "worker-a@example.invalid", "ai": {"status": "waiting", "summary": "waiting for deploy approval", "evidence": "Do you want to proceed? (y/n)", "digest": "sha256:0a1b2c3d4e5f60718293a4b5c6d7e8f90a1b2c3d4e5f60718293a4b5c6d7e8f9", "source": {"machine": "host-a", "session": "$4:1712400000"}, "model": "example-model", "updatedAt": "2026-10-25T05:41:30.000Z"}}
]}
```

AI object fields ([`team-snapshot.json#/$defs/ai`](schemas/team-snapshot.json)):

| Field | Meaning |
|---|---|
| `status` | `working`, `waiting`, `idle`, `unknown` (model output; distinct from the classifier `state`) |
| `summary` | one-line progress, target ≤ 20 characters, hard cap 80 |
| `evidence` | last ≤ 600 characters of the **redacted** pane text the summary was based on |
| `digest` | `sha256:<hex>` of the normalized pane text + model + prompt version |
| `source` | `{machine, session}` the content came from |
| `model` | model identifier used |
| `updatedAt` | generation time |

### 6.6 Heartbeat, reconnect, backpressure

- If the server has sent nothing for 25 s it sends `{"type":"pong","time":…}` without `id`.
  The server never closes a connection for client silence.
- Clients SHOULD reconnect when they have received **no message for 60 s**, using exponential
  backoff from 1 s to a 30 s cap with full jitter, then re-`sub` with their last applied `seq`
  values.
- Each connection has a send queue of 64 messages. If it fills (slow consumer) the server closes
  the connection with code `4429`; the client reconnects and recovers via replay.
- Limits: 64 concurrent connections globally, 8 per token; client frames ≤ 4 KiB; ≤ 64 projects
  per `sub`.

Close codes: `4401` unauthorized (token revoked), `4429` slow consumer, `1001` server shutdown,
`1008` protocol violation (e.g. binary frame, oversize frame).

## 7. Agent report

`POST /api/v1/agent/report` with an `agent` token, over persistent HTTP/1.1 keep-alive.
Request ([`agent-report.json`](schemas/agent-report.json)), response
([`agent-report-response.json`](schemas/agent-report-response.json)).

### 7.1 Request

<!-- schema: agent-report.json -->
```json
{
  "agent": {"version": "0.1.0", "boot": "3f6c2a9e-8d41-4b7a-9c55-0e2f1a6b7c8d", "seq": 812},
  "full": false,
  "tmux": {"server_pid": 1234, "ok": true},
  "panes": [
    {"sid": "$3", "created": 1712345678, "name": "worker-example-project-host-a-codex", "pane": "%7",
     "path": "/srv/example-project", "cmd": "node", "child": "codex", "activity": 1712349999,
     "state": "running", "detail": "", "ctx_pct": 41, "model": "example-model",
     "last_line": "Running go test ./internal/store", "box": "worker-a@example.invalid", "project": "example-project"}
  ],
  "removed": ["$5:1712000000"],
  "content": [
    {"sid": "$3", "created": 1712345678, "digest": "sha256:9f2c1b7e4a3d5f60718293a4b5c6d7e8f90a1b2c3d4e5f60718293a4b5c6d7e8",
     "text": "$ go test ./internal/store\nok  example/internal/store 0.41s"}
  ]
}
```

- `agent.boot` is a UUID generated at agent start; `agent.seq` increases by 1 per report within a
  boot. There is **no machine field**: the machine is the token's. A body that names one is not an
  error, but the value is ignored.
- `panes` has **one entry per tmux session** (the session's active pane), keyed by
  `(sid, created)`. `pane` is that pane's id, for display only.
- `state`/`detail`/`ctx_pct`/`model`/`last_line` come from the agent's classifier. `state` is one of
  the values in §6.4 except that the agent sends `unknown` for a session it has not classified yet.
- `box`/`project` are read from the session's working directory mailbox config, empty if none.
- `tmux.ok: false` means the tmux server is not reachable; `panes` is then empty and the service
  treats every session on the machine as absent.

### 7.2 Full, incremental, heartbeat

| Kind | When | Semantics |
|---|---|---|
| full (`full: true`) | at start, every 60 s, and after a response with `resync: true` | `panes` is the complete session set; any session the server knew for this machine and not listed is removed; `removed` MUST be empty |
| incremental (`full: false`) | on change | `panes` = new or changed sessions (whole entry); `removed` = session keys that disappeared |
| heartbeat | 10 s without any change | an incremental report with empty `panes`/`removed`/`content` |

The agent does not queue history while disconnected: it keeps only the latest state per session
and sends a full report first after reconnecting (backoff 1 s → 15 s).

### 7.3 Response

<!-- schema: agent-report-response.json -->
```json
{"ack": 812, "want_content": ["$3:1712345678"], "resync": false, "min_agent": "0.1.0"}
```

- `ack` echoes the accepted `agent.seq`.
- `resync: true` asks for a full report next. The server sets it when it has no baseline for this
  `(machine, boot)` and received an incremental report (e.g. after a service restart), or when
  `agent.seq` went backwards within a boot. The incremental report is still applied as far as it goes.
- `want_content` lists session keys whose content the server wants (§7.4). It is the complete
  current list each time, not a diff.
- `min_agent` is the minimum agent version the server accepts.

### 7.4 Content (`want_content`)

- `want_content` only ever contains sessions matched to **roster members** of some project.
  **Content of non-member sessions never leaves the machine.** Before the AI subsystem is enabled
  the list is always empty.
- The agent sends `content` only for wanted sessions, only when the digest changed, at most once
  per session per 10 s, and at most 32 KB/s per machine. `text` is already redacted by the agent,
  ≤ 80 lines and ≤ 16 KiB. The digest is computed over normalized text (ANSI stripped, whitespace
  folded, timer digits replaced by `#`).
- The server redacts again, keeps only the latest text per session in memory, never persists it,
  and silently discards content for sessions it did not want.

### 7.5 Staleness and versions

- A machine with no accepted report for 30 s is **stale**: the server pushes
  `machine{online:false}` and re-pushes that machine's live items with `stale: true`. The next
  accepted report pushes `machine{online:true}`.
- If `agent.version` (semver) is lower than `min_agent`, the server answers
  `426 agent_outdated` with `error.min_agent` set, and discards the report. The agent SHOULD keep
  running, log the condition, and retry no more than every 5 minutes.

<!-- schema: error.json -->
```json
{"error": {"code": "agent_outdated", "message": "agent 0.0.9 is older than 0.1.0", "min_agent": "0.1.0"}}
```

- Other statuses: `401` bad token, `403 forbidden` non-agent token, `413` body too large,
  `422` schema violation, `429 rate_limited` above 10 reports/s per machine.

## 8. AI summaries (server side)

Clients only display AI data (§6.5). This section is informative so clients know what to expect.

### 8.1 Triggers and caps

- A member is re-summarized when its content digest changed **and** one of: the session left
  `running` (to idle/waiting/stuck) and stayed ≥ 5 s; content has been still for ≥ 20 s; or it has
  been `running` for > 5 min since the last summary. At most once per member per 120 s.
- Concurrency 2, request timeout 30 s; ≤ 30 calls per project per hour, ≤ 1500 per day globally;
  a daily spend cap stops summarization until the next day once reached; 5 consecutive failures
  open a 10-minute circuit breaker.
- The model never decides `state`; it only writes `status` + `summary`.

### 8.2 Data handling

- Only roster members' content is ever requested (§7.4). Both agent and server redact secrets
  (API keys, tokens, `Bearer …`, `KEY=…` assignments, URL credentials, PEM private keys, long
  high-entropy strings) to `«redacted:<kind>»`; text that is more than 30 % redacted is not sent
  to the model and the member is marked `unknown`.
- The service stores per member only: status, summary, ≤ 600 characters of redacted evidence,
  digest, source, model, time. Full pane text is held in memory only (latest copy).

All schemas are JSON Schema draft 2020-12 and **self-contained**: each file carries the
definitions it needs under `$defs` and refers to them only as `#/$defs/<name>`. A definition
name used in several files MUST be identical in all of them (it is a copy, not a variant), so the
files can be compiled independently without a reference resolver. Change a shared definition in
every file at once.

Schemas describe shape. Rules they cannot express — key derivation, "trimmed non-blank", the
silent drop of an invalid `id`, cross-field identity checks, roster byte size — are normative in
the prose above.

## 中文摘要

- 团队服务替代原「桌面经 SSH 读写名单 JSON」的方式：名单与 AI 摘要持久化、走 `seq` 事件可回放；
  面板实时状态由各机 agent 上报、走 `lseq` 不落库不回放。
- 令牌三类：`lead`（单项目，可导入导出）、`desktop`（全部或白名单项目）、`agent`（单机，只能上报）；
  worker 不发令牌。令牌只能在服务主机本地签发，没有 HTTP 管理接口。
- 写入只走 REST。改位置字段（host/port/username/workdir/tmux）须带前置条件：PATCH/DELETE 用
  `If-Match`，批量 PUT 用条目内 `rev`；缺失或不符一律 412。DELETE 另需 `?tmux=<id>:<created>`，不符 409。
- 成员字段校验逐条移植自 `team_members.py`（100 人、256 KiB、备注 2000 字、各字段长度与正则），
  以 Python 生成的判例为准。客户端写任何 AI 字段 403；导入时旧文件里的 AI 字段丢弃不报错。
- WS 子协议 `dssh-team.v1`，只推不收写；订阅带 lastSeq，窗口内回放 delta，窗口外或超前发
  `resync`+快照；之后总发一次 live 全量作为确认。25s 心跳、60s 无消息重连、队列 64 满即断。
- agent 上报每会话一条，启动/每 60s/resync 发全量，变化发增量，空闲 10s 发空增量当心跳；
  `want_content` 只含名单成员，非成员面板内容永不离机；30s 无上报标 stale；低于 `min_agent` 回 426。

### Live branch metadata

A live item may include `branch` (string, at most 200 characters) for an exact matched agent session. Empty or unmatched values are omitted. This is display-only metadata: clients must not derive task IDs from branch text. Task titles use the taskboard collector’s existing bound task and brief queries, with the roster current task as fallback.
